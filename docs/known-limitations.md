# Known limitations

Everything listed here is a deliberate scope decision or a measured weakness, not a hidden defect.

## Machine learning
- **Synthetic data only.** The simulator has three failure modes with clean physical signatures. Real equipment has more failure modes, sensor faults, operating-regime changes and label noise (maintenance logs are often incomplete). Expect lower real-world performance, and re-evaluate on real failure history before anyone acts on predictions.
- **Calibration is imperfect.** On the time holdout, mid-range probabilities are under-confident: predicted 0.38 corresponded to an observed 0.66 failure rate (see `ml/reports/evaluation.md`). The isotonic calibrator is fit on about 20 % of units, which is a small sample. Risk levels therefore err on the cautious side.
- **Calibrated vs. uncalibrated ranking.** The calibrated production model's holdout PR-AUC (0.795) is a little lower than the same algorithm uncalibrated (0.829). That's because it trains on 80 % of units, keeping 20 % back for calibration.
- **RUL is weak.** MAE is 10.8 days vs. 14.8 for a constant baseline. It does not sharpen near failure. Right-censoring (units that have not failed yet) is ignored; survival models (Cox, AFT) would be the principled next step.
- **No hyper-parameter tuning.** The models use fixed, sensible defaults. Tuning properly requires nested cross-validation.
- **Small-fleet sensitivity.** With 20 units × 180 days, holdout PR-AUC drops to about 0.51. Few failures means high variance.
- **Explanations are model explanations, not root-cause analysis.** SHAP describes what drove the model's output. The "suspected failure mode" is a deterministic mapping from those drivers.
- **Recommendations are fixed rules**, deliberately not generated by an AI model, and are labelled as such.

## Platform
- **Login rate limiter is per process.** With several API replicas, each enforces its own limit. Production answer: a shared store (Redis) or an AWS WAF rate-based rule.
- **Ingestion is batch, not streaming.** There is no MQTT / OPC-UA / Kafka connector. The REST batch endpoint is the integration point; the Fraud Detection Engine (a separate repository) shows streaming with Kafka.
- **Scoring is on-demand or event-driven.** Units are re-scored after new data is ingested, on activation of a model, or by `score-all`. There is no built-in periodic scheduler. In production, use an EventBridge schedule (or cron) that runs `python -m app.cli score-all`.
- **Single-tenant.** There is no organisation separation, and all users see all equipment.
- **No e-mail or SMS notifications for alerts.** Alerts appear in the UI only. On AWS, CloudWatch alarms notify operators about *platform* health, not equipment risk.
- **Readings partitions are created on demand** by the ingestion code. There is no automatic retention policy; old partitions can be dropped manually (see OPERATIONS.md).

## Testing and infrastructure
- **S3 code paths:** the CSV upload hand-off is tested against a fake S3 client; `S3ArtifactStore` (model artifacts in S3) is **not covered by automated tests**. Neither has been run against real AWS.
- **Terraform has not been applied to a real AWS account, and was not validated locally** (the Terraform CLI was not available in the development environment). CI runs `terraform fmt -check` and `terraform validate` on every push. Review the plan output carefully before the first `apply`.
- **No concurrent load test yet.** A single-client check (`e2e/perf_check.py`, Docker on a 4-vCPU machine) measured 13,384 readings/s REST ingestion and prediction p50 128 ms / p95 242 ms (n = 40), which meets the design targets. Behaviour under many concurrent clients is unmeasured; a Locust or k6 test is the next step before production.
